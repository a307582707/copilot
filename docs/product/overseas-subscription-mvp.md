# 海外订阅服务 MVP 定义

## 结论

第一阶段不要做“大而全”的节点市场，先做一个能收款、能交付、能退款、能封禁、能支撑客服的最小闭环。

如果第一阶段就铺很多地区、很多套餐、很多协议，最后最先失控的通常不是技术，而是成本、客服和风控。

## 1. 第一阶段目标

首发阶段只验证三件事：

1. 用户是否愿意为这类服务真实付费
2. 支付、订阅、交付和客服链路能否顺畅闭环
3. 单用户成本、退款率和工单量是否在可承受范围内

只要这三件事还没跑清楚，就不建议扩很多地区或做复杂套餐矩阵。

## 2. MVP 范围

### 2.1 地区

只保留 `1-2` 个地区：

- 1 个主区域
- 1 个备用区域

选择标准：

- 供应商库存稳定
- 支付用户主要分布和时区匹配
- 投诉和封禁处理路径清晰
- 成本可预估，不靠短期促销或灰色资源

### 2.2 套餐

首发只做两种权益：

| 套餐 | 说明 |
| --- | --- |
| Trial | 有时间和配额限制，不等于正式用户体验 |
| Monthly | 单月订阅，自动续费可后置 |

先不要做：

- 年付
- 家庭套餐
- 多档速率套餐
- 不同协议分套餐
- 无限设备数

### 2.3 支付链路

第一阶段只保留 `1` 条正式收款链路：

- 首选：支持海外用户、支持 webhook、支持退款和争议处理的支付商

如果支付链路还没跑通，可以先做受控内测，但不建议公开售卖。

### 2.4 支持渠道

第一阶段只保留 `1` 套主支持渠道：

- 工单或邮件二选一
- 即时通讯只做辅助，不要当唯一正式渠道

原因很简单：没有统一工单入口，后面退款、封禁和故障通知都会乱。

## 3. 第一阶段用户闭环

MVP 必须覆盖下面完整路径：

1. 用户注册
2. 邮箱验证或其他最小身份校验
3. 试用或购买月付套餐
4. 支付成功后订阅激活
5. 用户在控制台获取配置或订阅信息
6. 到期提醒、续费、失效处理
7. 用户可发起退款或支持请求
8. 后台可暂停、封禁、补偿或回收

只做“支付成功后发一段文本给用户”不算完整交付。

## 4. 第一阶段不做什么

明确砍掉下面这些内容：

- 多国家大规模铺点
- 多协议矩阵
- 智能选路和复杂路由规则
- 大量营销型节点命名
- 自定义客户端分发体系
- 复杂联盟/分销体系
- 多支付商并行首发
- 24x7 实时人工支持承诺

## 5. MVP 功能表

| 模块 | P0 必须有 | P1 可后置 |
| --- | --- | --- |
| 官网/落地页 | 套餐、价格、退款、支持入口 | 营销内容 A/B 测试 |
| 账号 | 注册、登录、邮箱验证、密码重置 | 多因子认证 |
| 订阅 | Trial、Monthly、到期时间、状态切换 | 年付、优惠码、自动续费 |
| 支付 | 创建订单、回调、入账、退款记录 | 多币种、多支付商 |
| 交付 | 配置查看、订阅更新、设备数限制 | 多端自动同步 |
| 支持 | 工单入口、常见问题、公告 | 在线客服机器人 |
| 后台 | 用户、订单、订阅、封禁、审计 | 分层权限、复杂报表 |
| 风控 | 注册限速、试用限额、异常流量告警 | 风险评分模型 |

## 6. 套餐和限制建议

第一阶段套餐不要设计得太花，限制项比卖点更重要。

| 项目 | Trial | Monthly |
| --- | --- | --- |
| 时长 | 3-7 天 | 30 天 |
| 设备数 | 1-2 | 3-5 |
| 区域数 | 1 | 1-2 |
| 支持渠道 | 自助文档 + 工单 | 工单 |
| 退款 | 不适用 | 有条件支持 |
| 风控 | 更严格 | 正常策略 |

## 7. 扩容闸门

达到下面条件前，不建议继续扩国家或扩套餐：

| 指标 | 建议闸值 |
| --- | --- |
| 支付成功率 | 稳定 |
| 退款率 | 可控 |
| 工单量 | 团队能消化 |
| 试用转付费 | 有稳定转化 |
| 节点健康 | 主区域持续稳定 |
| 毛利 | 单用户收入覆盖资源和支持成本 |

## 8. 第一阶段交付物

这几个东西要么同时上线，要么就继续内测：

- 公开套餐页
- 账号与订阅页
- 最小支付链路
- 最小交付入口
- 最小支持入口
- 最小后台审计与封禁能力

## 9. MVP 完成定义

满足下面条件，才算第一阶段完成：

- 至少 1 个正式支付链路可用
- Trial 和 Monthly 两种订阅状态能跑通
- 用户支付后能稳定拿到交付结果
- 后台能查订单、改状态、封禁和记录审计
- 用户遇到问题有明确支持入口
- 到期、退款、封禁和故障都有处理路径
