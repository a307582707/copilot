# 海外订阅服务业务与合规清单

## 判断

这类项目最容易死在三件事上：

- 商户和托管商不接受你的业务类型
- 公开售卖后没有滥用控制，被投诉或封禁
- 支付、退款和客服扛不住，最后不是技术问题而是运营失控

所以第一阶段不应该问“买几台机器”，而应该先完成下面这份 go/no-go 清单。

## 1. 业务边界

在任何采购、开发和宣传前，先把下面几条写清楚：

| 项目 | 必须拍板的内容 |
| --- | --- |
| 服务对象 | 公众订阅用户，还是特定行业/社群用户 |
| 服务区域 | 支持哪些国家和地区，不支持哪些区域 |
| 服务形态 | 月付订阅、季付、年付，是否允许免费试用 |
| 支持渠道 | 工单、邮件、Telegram、Discord、站内消息 |
| 可接受使用政策 | 是否禁止垃圾邮件、爬虫、滥用 API、攻击流量、侵权流量 |
| 退款规则 | 几天内可退、什么情况不退、谁审批 |
| 数据保留 | 保留哪些账号、订单、交付、审计和滥用记录 |

如果这些边界写不清，后面的支付和客服都会变成扯皮。

## 2. 主体与合同文件

至少准备下面这些基础文件：

| 文件 | 目标 | 备注 |
| --- | --- | --- |
| Terms of Service | 定义服务边界、争议处理、退款和责任限制 | 必须对外可访问 |
| Privacy Policy | 说明采集哪些数据、为什么采集、保留多久 | 支付和托管商常会看 |
| Acceptable Use Policy | 约束滥用、违法流量和封禁规则 | 公开售卖时最好单独成文 |
| Refund Policy | 降低退款争议和客服扯皮 | 和支付商规则保持一致 |
| Support Policy | 说明响应时间、联系方式、服务窗口 | 避免用户默认你是 24x7 人工支持 |

建议把“支持什么、不支持什么”写得比营销文案更清楚。这个阶段宁可保守，也不要把 SLA、退款和节点承诺写得过满。

## 3. 支付渠道检查项

支付不是“能收款”就算完成，重点在是否允许这类业务持续经营。

### 3.1 付款渠道至少核实这些

| 检查项 | 说明 |
| --- | --- |
| Merchant onboarding | 商户开户是否接受该业务类型 |
| Prohibited business | 是否属于支付商禁止或高风险行业 |
| Chargeback policy | 拒付、争议和风控冻结怎么处理 |
| Refund support | 是否支持全额和部分退款 |
| Recurring billing | 是否支持订阅续费和失败重试 |
| Payout cycle | 结算周期、冻结周期、最低结算额 |
| Webhook reliability | 是否支持签名校验、重放防护、幂等处理 |
| Tax/VAT support | 是否能配合税务处理或第三方税务服务 |

### 3.2 不建议直接上线的做法

- 只有个人收款账号，没有正式商户能力
- 没有拒付预案，就直接开订阅自动扣款
- 一个支付商都没跑通，就先做大量市场投放

## 4. 托管商与上游资源检查项

这类业务很依赖托管商和上游网络资源。要确认的不是“能不能买到机器”，而是“买完会不会很快被封”。

| 检查项 | 说明 |
| --- | --- |
| Acceptable use | 托管商是否允许这类公开订阅业务 |
| Abuse process | 收到投诉后的处置时限和申诉流程 |
| Bandwidth policy | 共享带宽、超量费用、限速规则 |
| IP reputation | 新 IP 的信誉、是否容易被黑名单命中 |
| Region availability | 首发区域库存是否稳定 |
| Burst tolerance | 峰值流量时是否会被限流或封禁 |
| API / automation | 是否支持自动开通、标签、告警、回收 |
| Billing granularity | 按小时、按月、按流量还是按带宽计费 |

建议至少准备两个供应商方向，避免单一托管商出问题时整批用户都受影响。

## 5. 数据、隐私和审计

需要保留的数据，和不该保留的数据，要一开始就分开。

### 5.1 建议保留

- 用户主档
- 订单与支付回调
- 订阅状态变更记录
- 配置交付记录
- 管理员操作日志
- 滥用事件与封禁记录
- 节点健康与容量指标

### 5.2 不建议无边界保留

- 超出业务必要范围的流量内容
- 与服务交付无关的长期明细日志
- 未脱敏的第三方密钥和明文凭据

日志和配置数据必须分层管理，避免“为了排查方便”把敏感信息混进普通业务状态。

## 6. 滥用控制最低要求

公开售卖场景里，没有风控就等于等着被投诉。

最低要求建议包括：

- 注册限速：按 IP、邮箱域名、支付指纹做频控
- 试用门槛：试用账号要有限制，不要和付费账号同配额
- 交付限速：短时间重复拉取配置、重复设备绑定要告警
- 异常流量：单用户带宽、会话数、区域切换异常要能看见
- 人工封禁：后台可暂停订阅、冻结配置、保留证据
- 申诉流程：封禁和退款至少有最小人工复核路径

## 7. 上线前 go/no-go 清单

下面这些项没完成，就不建议公开售卖：

| 检查项 | 状态 |
| --- | --- |
| 主体、服务条款、隐私政策、AUP 已成文 | 待确认 |
| 至少 1 个支付渠道确认可接受该业务 | 待确认 |
| 至少 1 个托管商确认可接受该业务 | 待确认 |
| 退款规则和争议处理流程已定义 | 待确认 |
| 支持渠道和响应窗口已定义 | 待确认 |
| 滥用控制与封禁流程已定义 | 待确认 |
| 审计日志、订单、订阅和配置交付可追踪 | 待确认 |
| 故障公告和状态页机制已准备 | 待确认 |
