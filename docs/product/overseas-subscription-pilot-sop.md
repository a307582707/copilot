# 海外订阅服务试运营 SOP

## 判断

试运营阶段的重点不是冲量，而是把这几条跑顺：

- 支付成功后能稳定交付
- 出故障时能快速收敛影响
- 用户能找到支持入口
- 退款、封禁和下线有证据、有记录、有回滚

如果这些还没有形成 SOP，就不适合放大流量。

## 1. 试运营目标

试运营阶段只做三类验证：

| 类别 | 验证目标 |
| --- | --- |
| 业务 | 是否有人真实付费、试用能否转付费 |
| 运维 | 交付、到期、续费、退款、故障、回收能否闭环 |
| 风控 | 滥用、投诉、拒付、异常流量是否可控 |

## 2. 试运营前检查

上线前至少逐项确认：

| 检查项 | 要求 |
| --- | --- |
| 支付 | 订单、回调、失败重试、退款都已联调 |
| 订阅 | Trial、Monthly、到期、暂停、取消可切换 |
| 交付 | 用户能获取配置，过期后可回收 |
| 支持 | 工单/邮件入口可用，有回复模板 |
| 风控 | 注册限速、试用限额、人工封禁可用 |
| 审计 | 管理员改订阅、退款、封禁有日志 |
| 监控 | API 健康、支付成功率、节点健康、工单量可观测 |
| 公告 | 有对外公告和状态页机制 |

## 3. 每日值守清单

试运营期间建议每天至少两次检查下面这些项：

| 检查项 | 关注点 |
| --- | --- |
| 新增订单 | 支付成功率、失败原因、异常退款 |
| 订阅状态 | 即将到期、激活失败、宽限期用户 |
| 配置交付 | 交付失败、拉取过频、设备异常切换 |
| 节点健康 | 在线率、时延、容量、区域异常 |
| 工单和邮件 | 高频问题、退款请求、故障投诉 |
| 风控事件 | 异常注册、异常带宽、封禁申诉 |

建议固定一个简短日报模板，不要靠聊天记录拼现场。

## 4. 关键指标

### 4.1 业务指标

| 指标 | 含义 |
| --- | --- |
| Trial 转付费率 | 试用是否有实际价值 |
| 支付成功率 | 支付体验是否顺畅 |
| 月退款率 | 定价、交付和客服是否有问题 |
| 拒付率 | 风控和支付商风险是否抬头 |

### 4.2 运维指标

| 指标 | 含义 |
| --- | --- |
| 配置交付成功率 | 用户能否拿到可用交付 |
| 节点在线率 | 区域级稳定性 |
| 容量使用率 | 是否接近扩容阈值 |
| API 健康状态 | 账单、订阅、交付接口是否稳定 |

### 4.3 支持与风控指标

| 指标 | 含义 |
| --- | --- |
| 单日工单量 | 团队是否扛得住 |
| 首次响应时长 | 用户支持体验 |
| 封禁率 | 滥用是否抬头 |
| 误封申诉率 | 风控策略是否过紧 |

## 5. 事件分级

### P1

满足任一条件按 P1 处理：

- 支付大面积失败
- 付费用户大面积无法获取交付
- 主区域整体不可用且无备用区域承接
- 账单、订阅状态出现明显错乱

处理要求：

- 立即暂停新增投放
- 在状态页或公告渠道发出说明
- 暂停自动续费或自动交付中的高风险动作
- 保留现场证据和时间线

### P2

- 单个区域容量告急
- 局部支付渠道抖动
- 工单量突增但核心链路未中断

处理要求：

- 降低新增用户导入
- 切备用区域或临时降配
- 评估是否需要临时退款/补偿

## 6. 退款 SOP

建议统一按下面流程处理：

1. 用户提交退款请求
2. 支持侧核对订单、订阅状态、交付记录和工单历史
3. 判断是否命中退款政策
4. 通过后台执行退款或部分补偿
5. 写入退款记录和管理员审计
6. 如需停用服务，同步回收交付和订阅状态

不要只退支付，不改订阅和交付状态，否则很容易留下“已退款但仍在用”的漏洞。

## 7. 封禁与申诉 SOP

### 7.1 触发条件

- 异常注册和异常试用
- 异常高流量或异常区域切换
- 收到托管商或支付商投诉
- 命中明确的 AUP 禁止项

### 7.2 处理步骤

1. 记录证据
2. 临时冻结账号或交付
3. 标记事件等级和处理人
4. 视情况通知用户
5. 支持申诉复核
6. 最终决定保留在 `abuse_events` 和审计日志中

## 8. 故障回滚 SOP

### 8.1 支付故障

- 关闭受影响支付渠道的新订单入口
- 保持已成功订单的入账幂等校验
- 必要时切人工补偿或延长订阅

### 8.2 交付故障

- 停止新的交付下发
- 保留现有可用配置不主动回收
- 先恢复主链路，再补失败交付

### 8.3 节点故障

- 切备用区域或暂停新用户分配
- 不承诺“秒级恢复”，先控影响面
- 对受影响用户做公告和补偿评估

## 9. 退出试运营的条件

满足下面条件，才建议进入下一阶段扩量：

- 支付和退款流程稳定
- 试用转付费有稳定数据
- 工单量处于团队可承受范围
- 主区域和备用区域的稳定性已验证
- 风控与封禁流程没有明显漏口
- 单用户毛利为正，且不是靠临时补贴撑起来

## 10. 试运营失败时的收缩路径

如果试运营数据不成立，建议按下面顺序收缩：

1. 先停止市场投放和新增试用
2. 保留存量用户支持与到期处理
3. 停止扩地区和扩套餐
4. 结清退款、争议和客服尾项
5. 回收闲置资源，保留账务和审计数据

这样做的好处是不会把试运营失败拖成长期亏损和客服黑洞。
