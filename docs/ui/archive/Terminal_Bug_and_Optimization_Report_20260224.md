# CodeSprite 终端模块 (Terminal) 深度评测与优化清单

## 一、当前“伪终端”的 BUG 与体验缺陷 (Feature Gaps)

根据深度体验与底层架构分析，当前页面左下方的“黑框终端”在交互上存在以下严重缺陷（由于其基于 HTTP 短连接实现，而非 WebSocket PTY）：

### 🔴 1. 致命级缺失 (阻断正常运维)
*   **不支持任何交互式命令：** 运行 `vim`、`nano`、`top`、`htop`、`mysql` 等需要霸占整个屏幕并捕获键盘按键的命令时，要么会直接被后端拉黑报错（"Interactive command is not allowed"），要么会导致请求一直挂起直至超时。
*   **上下文/状态丢失 (无状态的 Shell)：** 你在这个黑框里执行 `cd /var/log`，然后紧接着执行 `pwd`，结果依然是 `/root`。因为每次敲击回车，系统都是新开一个隔离的 SSH Session 执行单条命令。不支持 `export` 环境变量供下一条命令使用。

### 🟡 2. 高优级体验缺失 (极其违背终端直觉)
*   **按键捕获失效：**
    *   不支持按 `↑` 和 `↓` 键调出历史命令，运维人员必须痛苦地重新手打长命令。
    *   不支持按 `Tab` 键自动补全文件名或路径。
    *   不支持使用 `Ctrl + C` 发送 SIGINT 中断信号来强行停止一个死循环的脚本。
*   **长时间运行命令处于“盲盒”状态：** 执行 `ping -c 10 localhost` 或 `sleep 20` 时，黑框里一片死寂，用户看不到进度，也不知道是卡死了还是在执行中。真正的终端是会一行一行往外吐日志的（流式输出）。
*   **视觉与右键菜单极度简陋：** 没有类似 Xshell 的原生右键菜单（如“右键直接粘贴”、“选中即复制”、“清屏”等快捷功能）。

## 二、给产品与开发团队的优化建议

如果要将 CodeSprite 打造成一个**合格且能收钱的 SRE 工作站**，对于终端模块必须进行以下两阶段的改造：

### 阶段一：产品定位重塑（本周可做：修改 UI 与预期）
既然现在做不到真实的 PTY 终端，就不要在 UI 上把它“伪装”得像一个真正的黑框终端，这只会拉高用户的心理预期然后导致失望。

1.  **修改命名与文案：** 将“终端”面板改名为 **“命令下发器 (Remote Exec)”** 或 **“单行终端”**。
2.  **添加占位符提示 (Placeholder)：** 在黑框或输入区域明确写上：“*此为单次命令执行通道。暂不支持 `vim`/`top` 等交互式命令，不支持 `cd` 维持目录状态。*”
3.  **加上下键历史记录 (前端极易实现)：** 让前端开发在那个 input 框上加一个键盘事件监听，把用户最近敲过的 50 条命令缓存在内存里，按 `↑` `↓` 就能切换。这能极大缓解没有真实终端的痛苦。

### 阶段二：底层架构推翻重做（P0级需求：彻底升级为 PTY）
要在下一个核心大版本中，把现在的假终端彻底替换掉：

1.  **引入 xterm.js (前端)：** 废弃现在的黑框，直接使用业界标准的 [xterm.js](https://xtermjs.org/) 组件。它是 VS Code 和所有网页版 SSH 堡垒机底层的终端渲染引擎。
2.  **实现 WebSocket 通信 (后端)：** 
    *   废弃现有的 `/api/ssh/exec` (将其转为纯后台 AI 使用的 tool-call 接口)。
    *   新增 `/api/ssh/pty/ws` WebSocket 路由。
    *   利用 Python 的 `paramiko` 调用 `chan.get_pty()`，将后端分配到的真实 Linux PTY 的 `stdin/stdout/stderr` 数据流，通过 WebSocket 实时双向转发给前端的 xterm.js。
3.  **成果验收：** 只有当用户能在网页上输入 `vim config.yaml` 且页面完美变身编辑器时，这个终端模块才算真正及格。
